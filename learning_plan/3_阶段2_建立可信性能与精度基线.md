# 阶段 2 指导：建立可信的性能与精度基线

> 对应总计划的阶段 2  
> 建议用时：3～4 天  
> 本阶段原则：先保证测量可信，再比较优化；保留一份固定基线。

## 一、学习目标

完成本阶段后，你应能：

1. 正确排除首次加载时间；
2. 区分 Host 墙钟、Device task、aicore time 和 replay 时间；
3. 建立可复现的正式三次验收流程；
4. 使用多种输入验证精度；
5. 为每次优化保留完整、可比较的实验记录。

## 二、固定实验条件

后续比较至少保持以下条件一致：

```text
硬件：同一台 Ascend 310P3
Device：NPU 3，通过 ASCEND_RT_VISIBLE_DEVICES=3 映射为程序内 npu:0
Shape：M=1，K=7168，N=16160
Dtype：输入/输出 FP16，L0C FP32 累加
Block Num：8
baseN=160，baseK=64，l1K=256
正式口径：预热 1 次，正式执行 3 次
```

不要一边更换 Device、输入、编译选项和 Tiling，一边比较性能，否则无法归因。

执行：

```

`matmul_m1.py:25-38` 已采用：

每次调用后同步，再停止墙钟计时。
```

预热不计入结果，首次动态库加载、kernel 加载和首次初始化不应污染正式三次。

```text
2.766～2.781 ms
```

不同轮次出现小幅波动是正常现象。不要为了让结果“好看”而删除较高值；应保留原始数据并说明波动。

## 四、Device 基线

普通应用级 profiling 可使用：

```bash
ASCEND_RT_VISIBLE_DEVICES=3 msprof \
  --application="python3 /home/l00949281-benchmark/ExampleMatmulM1/matmul_m1.py" \
  --output=/home/l00949281-benchmark/ExampleMatmulM1/msprof_learning_baseline
```

重点读取：

- `task_time_*.csv`：整个 Device task 的开始、结束和持续时间；
- `op_summary_*.csv`：算子及管线汇总；
- `op_statistic_*.csv`：多次调用的统计平均；
- `msprof_*.json`：应用级 Timeline。

当前 `task_time` 中第一次是预热，正式三次为：

```text
Task ID 3：2638.519 μs
Task ID 4：2642.652 μs
Task ID 5：2637.977 μs
平均：     2639.716 μs
```

注意：`op_statistic` 中约 2644.983 μs 的平均包含预热，共四次，不能替代正式三次平均。

## 五、单算子 profiling 基线

完整指标采集命令：

```bash
ASCEND_RT_VISIBLE_DEVICES=3 msprof op \
  --application="python3 /home/l00949281-benchmark/ExampleMatmulM1/matmul_m1.py" \
  --output=/home/l00949281-benchmark/ExampleMatmulM1/msopprof_learning_baseline \
  --aic-metrics=BasicInfo,PipeUtilization,ArithmeticUtilization,Memory,MemoryL0,MemoryUB,ResourceConflictRatio \
  --kernel-name=matmul_lyc_custom \
  --launch-count=1 \
  --launch-skip-before-match=1 \
  --replay-mode=kernel \
  --kill=off \
  --warm-up=0
```

这里：

- `launch-skip-before-match=1` 跳过 Python 中的预热；
- `launch-count=1` 只采集随后的一次匹配 kernel；
- `replay-mode=kernel` 会重放 kernel，以采集多组硬件指标；
- 应用程序打印的几十到几百毫秒包含重放等待，不能作为优化成绩。

单算子成绩应读取工具输出的 `Task Duration` 或产物中的对应 Device 指标，而不是应用墙钟。

## 六、精度验收指导

每次代码或 Tiling 改动后，至少进行以下测试。

### 1. 多 seed 随机输入

建议保留：

```text
seed = 0、1、42、2026
```

对比自定义算子和参考 `torch.mm`，记录：

```text
max_abs
mean_abs
是否全部 finite
输出 shape 和 dtype
```

当前基线在这些 seed 上曾达到 `max_abs=0、mean_abs=0`。后续实现发生变化时，不应预先假设仍然逐元素完全相等，应根据 FP32 累加顺序、FP16 输出和参考实现明确容差。

### 2. 全一输入

```text
A 全一，B 全一；
C 的每个元素应为 7168。
```

### 3. 定向输入

建议新增：

- A 仅一个位置为 1，其余为 0：检查 K 方向选取；
- B 仅一列为 1，其余为 0：检查 N 方向和输出偏移；
- 不同位置使用不同数值：降低全一输入掩盖索引错误的概率；
- 极大、极小和含零输入：检查转换和数值范围，但不要用 NaN/Inf 作为普通精度验收输入。

## 七、实验记录模板

每次实验建立一行：

| 字段 | 内容 |
|---|---|
| 实验编号 | 例如 E01 |
| 基线版本 | 固定基线标识 |
| 唯一修改项 | 只允许一个主要变量 |
| 编译配置 | 保持记录 |
| 普通运行三次 | 保留原始值 |
| Device 正式三次 | 保留原始值 |
| 平均与波动 | 不只记录最优值 |
| 精度 | 多 seed、全一、定向输入 |
| profiling 指标 | 记录与假设有关的指标 |
| 结论 | 接受、拒绝或无法判断 |
| 下一步 | 根据证据决定 |

性能变化建议统一计算：

```text
加速比 = 基线时间 / 优化后时间
时间变化率 = (优化后时间 - 基线时间) / 基线时间 × 100%
```

时间变化率为负才表示耗时下降。写报告时优先使用加速比和“耗时降低百分比”，避免正负号混乱。

## 八、课后题

### 题 1：复算正式 Device 平均时间

根据 2638.519、2642.652、2637.977 μs，复算正式三次平均值。

### 题 2：为什么不能使用 op_statistic 的四次平均？

四次平均约 2644.983 μs，它和正式三次平均有什么区别？

### 题 3：端到端与 Device 的差值是什么？

如果某轮端到端平均为 2.780 ms，Device 正式三次平均为 2.639716 ms，差值约多少？能否把这个差值全部称为“kernel launch API 时间”？

### 题 4：为什么还要 synchronize？

如果三次调用只在循环结束后统一同步，所得每次时间是否还是每次 MatMul 的端到端时间？

### 题 5：三次和更多次测量是否矛盾？

项目要求预热一次、正式三次取平均。调优时能否额外运行 10～20 次判断波动？

### 题 6：msopprof 打印 88 ms 是否说明优化严重退化？

已知普通 Device task 约 2.64 ms，而 `msopprof --replay-mode=kernel` 运行时 Python 打印平均 88 ms，应如何判断？

### 题 7：全一输入精度通过是否足够？

一个实现把若干 B 元素交换了位置，但 A、B 全为 1。全一测试能否发现？应增加什么测试？

### 题 8：一次实验提高 0.5%，能否直接宣布有效？

还需要哪些信息？

## 九、参考答案

### 答案 1

```text
(2638.519 + 2642.652 + 2637.977) / 3
= 2639.716 μs
```

### 答案 2

`op_statistic` 的四次平均包含预热调用，而项目正式成绩定义为预热后的三次。二者的样本集合不同。预热时间即使接近正式调用，也不能为了统计方便改变验收口径。

### 答案 3

```text
2.780 ms - 2.639716 ms = 0.140284 ms ≈ 140.284 μs
```

这是不同测量口径下的近似差值，包含 Host 侧调用准备、Tiling、launch、同步及测量等开销，不能全部归为某一个 launch API。若来自不同运行轮次，还包含运行波动，只能近似比较。

### 答案 4

不能。NPU 调用是异步的，如果不在每次调用后同步，单次计时可能主要反映提交任务的时间，并把多个 Device 任务累计到最后一次同步中。当前每次同步的口径适合测量单次要等待结果完成的端到端延迟，但同步本身也有开销，应与 Device task 分开报告。

### 答案 5

不矛盾。保留“预热一次、正式三次”作为项目统一验收口径；额外 10～20 次用于研究稳定性和减少偶然波动。报告时明确区分两组数据，不能悄悄用更多次平均替代正式三次。

### 答案 6

不能据此判断退化。kernel replay 会重复执行和等待，应用墙钟包含采集与重放成本。应比较同口径的 `Task Duration`、普通 profiling 的 `task_time` 或非 replay 的普通运行结果。

### 答案 7

不能，因为全一输入对很多交换不敏感。应让 A 的不同 K 位置取不同值，或让 B 的不同列/行使用可区分数值，再与参考 MatMul 比较。随机输入和多 seed 也能显著降低这种漏检概率。

### 答案 8

不能。至少要知道重复测量波动、样本数、是否同 Device 同配置、精度是否通过以及结果是否可复现。如果普通波动本身超过 0.5%，该结果只能记为“无法区分于噪声”，需要更多测量或更大收益证据。

## 十、进入下一阶段的标准

- 有一份固定基线和完整原始数据；
- 能独立运行普通 profiling 和单算子 profiling；
- 每次修改后都有精度结果；
- 不再混用 replay 墙钟、Device task 和正式三次平均；
- 小于测量波动的差异不会被写成确定性优化结论。
