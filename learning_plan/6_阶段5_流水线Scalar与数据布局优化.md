# 阶段 5 指导：流水线、Scalar 与数据布局优化

> 对应总计划的阶段 5  
> 建议用时：1～2 周  
> 前置要求：完成阶段 1～4，已有固定基线和 Tiling 实验结果。  
> 本阶段原则：先保证依赖正确，再追求重叠；不要通过删除同步来“提速”。

## 一、学习目标

完成本阶段后，你应能：

1. 判断双缓冲是否真正形成软件流水；
2. 用指令账本定位 Scalar 和搬运控制开销；
3. 区分 Tiling 调整与数据通路重构；
4. 分析 A 补零、B 布局转换和输出提取的成本；
5. 在修改队列和事件后仍保证精度与同步正确。

## 二、先建立指令账本

当前基线的理论计数：

| 路径 | 代码 | 理论次数 | 硬件观测 |
|---|---|---:|---:|
| Cube | Mmad | 11,312 | 11,312 |
| MTE1 | SplitA LoadData | 11,312 | 与 SplitB 合计 56,560 |
| MTE1 | SplitB LoadData | 45,248 | 与 SplitA 合计 56,560 |
| MTE3 | zero UB→A1 | 2,828 | 与输出合计 2,929 |
| MTE3 | UB→GM 输出 | 101 | 与 zero 合计 2,929 |
| MTE2 | CopyB GM→L1 | 452,480 | 与 CopyA 主循环合计 497,728 |
| MTE2 | CopyA 第 0 行 GM→L1 | 45,248 | 硬件总计 497,736，尚余 8 次待解释 |

CopyB 的每次调用搬运一个 16×16 FP16 分形：

```text
16 × 16 × 2 = 512 字节
452,480 × 512 = 231,833,600 字节
```

这恰好等于 B 的逻辑字节数。由此可以形成一个重要判断：

> 当前 MTE2 指令很多，并不只是因为 B 很大，也与每次按 16×16 分形组织搬运有关。只调 baseK，不会减少 CopyB 次数；只调 l1K 或 baseN，在当前算法下也不会改变 CopyB 理论总次数。

## 三、检查当前双缓冲是否充分利用

当前 `ComputeTile` 的高层顺序是：

```text
outer：
  CopyA(outer)
  CopyB(outer)
  DeQue A1/B1

  inner：
    SplitA
    SplitB
    DeQue A2/B2
    Mmad

  Free A1/B1
```

A1/B1/A2/B2 都申请了两块 Buffer，但源码没有显式采用：

```text
先发起 outer+1 的搬运
再处理 outer 的 Split/Mmad
```

这种明确的下一批预取结构。因此：

- 双缓冲提供了可重叠的存储条件；
- 不等于软件已经充分利用重叠；
- 也不能仅凭源码断言硬件完全没有异步重叠；
- 最终要通过队列重构实验和 profiling 验证。

## 四、实验 P1：减少不变量和地址计算

这是相对容易归因的第一项代码实验。

### 研究对象

`CopyB` 内层反复计算：

```cpp
uint32_t dstOffset = ...;
uint64_t srcOffset = ...;
```

同时存在多层循环、分形计数和运行时乘法。

### 实验约束

- 不改变 DataCopy 的次数；
- 不改变源地址和目的地址；
- 不改变 tile 参数；
- 只外提不变量、简化递推或减少重复计算。

### 预期

```text
MTE2 指令总数：不变
B 逻辑字节数：不变
Scalar active：可能下降
总时间：可能下降，也可能因 MTE2 关键路径而不变
```

如果 Scalar active 下降而总时间不变，应接受“关键路径未改变”的结果，而不是继续声称获得了端到端优化。

## 五、实验 P2：重构软件预取

### 目标

在不改变 tile 大小的条件下，让下一批 GM→L1 或 L1→L0 工作更早发起，研究它与当前 Mmad 的重叠。

### 实施前检查

1. 两块 Buffer 是否足够容纳当前批和预取批；
2. 当前批使用完毕前，是否可能被下一批覆盖；
3. `EnQue/DeQue/FreeTensor` 顺序是否匹配；
4. EVENT_ID 是否会发生跨阶段误复用；
5. 最后一个 outer 是否有越界预取；
6. L0C 累加顺序和 `cmatrixInitVal` 是否保持正确。

### 实验预测

```text
数学 FLOPs：不变
MTE2 主循环指令总数：基本不变
总时间：若供数等待是关键路径，应下降
Cube/MTE1 wait：可能改善，但不应预先保证某个百分比
```

### 禁止做法

不要直接删除 `WaitFlag` 或 `PipeBarrier` 观察是否“还能跑对一次”。数据竞争可能具有偶发性，一次精度通过不能证明同步正确。

## 六、实验 P3：研究 A 的重复补零和读取

### 当前行为

每个 N tile 的每个 outer：

- 将 `16×l1K` 的 zero UB 复制到 A1；
- 再读取原始 A 的第 0 行；
- 同样的 A 会在不同 N tile 中重复使用。

原始 A 的逻辑重复读取量：

```text
101 × 7168 × 2 = 1,447,936 字节
```

它远小于 B 的 231,833,600 字节，但补零、同步和指令次数仍可能有影响。

### 研究问题

- 是否每个 outer 都需要完整重写 A1 的零区域？
- 是否可以复用已初始化区域而不破坏队列语义？
- 是否可以将 A 的布局准备与 N tile 循环解耦？
- 即使 MTE3 指令减少，MTE2 关键路径是否决定总时间？

先写正确性不变式：A1 第 0 行对应当前 K 区间，其余 15 行必须始终为零。

## 七、实验 P4：重新设计 B 的搬运组织

这是更进阶、也更可能改变 MTE2 指令数的实验。

### 当前路径

```text
GM ND
  → 反复按 16×16 分形 DataCopy
L1 zZ
  → ifTranspose=true 的 LoadData
L0B nZ
  → Mmad
```

### 需要研究的不是“哪个参数更大”，而是

- 能否减少分形搬运调用次数；
- 能否改善 GM 连续访问和目的布局之间的匹配；
- 是否仍满足 L1 zZ 与 L0B nZ 的布局要求；
- 是否引入额外 UB/L1 转换，导致总成本反而增加；
- 修改后 MTE2、MTE1、Scalar 和总时间如何共同变化。

不能简单把多条 DataCopy 合并成一条而不验证 stride、分形间隔和对齐。建议先在一个 K/N 小分形上做地址推演，再实现完整版本。

## 八、实验 P5：尾部负载与输出路径

### 尾部负载

基线中 5 核执行 13 个 tile，3 核执行 12 个。可以结合阶段 4 的不同 N 划分判断尾部是否值得专门优化。

不要因为存在 1 个 tile 差异就假设总时间一定损失 `1/13`。只有尾部没有其他工作遮蔽且它位于最后完成核上时，才会明显暴露。

### 输出路径

当前每 N tile：

```text
L0C FP32 → UB FP16 → 提取第 0 行 → GM
```

MTE3 active 只有约 1.06%，MTE3 指令合计 2,929，输出本身通常不是第一优先级。优化输出前应先证明它位于关键路径。

## 十一、参考答案

### 答案 1

双缓冲只提供两块可交替使用的存储。是否有收益还取决于下一批工作是否提前发起、队列依赖、Buffer 生命周期以及搬运与计算是否真正重叠。当前代码没有显式完整的下一 outer 预取结构，因此需要软件流水实验，而不是把 Buffer 数量当作结论。

### 答案 2

此时：

```text
l1Prefetch = 256 / 128 = 2
每 N tile inner 总数 = 28 × 2 = 56

SplitA：101 × 56 = 5656
SplitB 每次 inner 执行 128/16=8 次：
       101 × 56 × 8 = 45248
MTE1 合计：50904
```

SplitB 总数不变，SplitA 减少，因此总 MTE1 指令从 56,560 降为 50,904。

### 答案 3

同步用于保证数据生产者和消费者之间的先后顺序。删除后可能出现旧数据、部分写入、Buffer 提前复用和偶发错误。一次正确可能只是时序碰巧满足，不能证明竞争不存在。优化应重构依赖并保持必要同步，再用多轮和定向输入验证。

### 答案 4

```text
101 × 7168 × 2 = 1,447,936 字节 ≈ 1.381 MiB
```

远小于 B 的约 221.1 MiB。但不能因此完全忽略，因为 CopyA 还包含补零、同步和指令控制开销；只是优化后是否影响总时间仍需实测。

### 答案 5

可以认为地址优化确实减少了一类硬件活动，但 Scalar 不是当前端到端关键路径，或其减少被 MTE2 等其他阶段遮蔽。应保留这个负结果，不应把 Scalar active 的改善直接换算为总时间收益。

### 答案 6

当前 CopyB 总次数由 `K×N/256` 决定，baseK 不参与 CopyB，l1K 和 baseN 在总循环中会约掉。要显著减少指令数，需要改变 B 的分形搬运和布局组织，而不是仅改变现有循环的分批大小。

### 答案 7

不一定。如果 B 是每次变化的输入，预打包成本必须计入；如果 B 是可复用的模型权重，预打包可以在初始化阶段完成，再报告稳态推理时间，但同时说明初始化成本和复用次数假设。不能只给优化后的 kernel 去掉必要转换，却不说明输入格式契约已改变。

### 答案 8

不是。低 active 只说明它不是优先性能瓶颈，功能正确性仍然重要。L0C→UB 的 FP32→FP16 转换、分形第 0 行提取和 GM 地址任何错误都会破坏结果，只是通常不值得先优化其速度。

## 十二、进入下一阶段的标准

- 至少完成 P1、P2 中的一项和 P3/P4 中的一项研究；
- 保留同步正确性说明和精度结果；
- 能区分“指令减少”“利用率改善”“总时间改善”；
- 能解释为什么某些结构优化需要重新设计数据通路，而不是继续扫参数；
- 至少形成一个有证据的负优化案例。
