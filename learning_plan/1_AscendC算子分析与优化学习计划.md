# ExampleMatmulM1 AscendC 算子分析与优化学习计划

## 1. 项目定位

可以把 `ExampleMatmulM1/matmul_lyc_custom` 当成一个完整的 **AscendC 算子性能实验项目**。它很适合学习：代码规模不大，但已经包含 Host Tiling、多级存储、双缓冲、Mmad、格式转换、流水线等待以及 Device/Host 性能差异。

建议不要一开始就盲目调参数，而是按照下面的闭环推进：

> **理解计算 → 建立可信基线 → 根据数据定位瓶颈 → 单变量实验 → 验证优化是否有效 → 总结适用边界**

---

## 2. 最终学习目标

完成整个路线后，应该能够独立回答以下问题。

### 2.1 算子在算什么

- 为什么这个 MatMul 实际更接近 GEMV？
- 为什么 M=1 仍要补齐到 16 行？
- B 在 GM、L1、L0B 中分别是什么布局？

### 2.2 时间花在哪里

- 为什么端到端约 2.78 ms，而 Device task 约 2.64 ms？
- MTE1、MTE2、MTE3、Cube、Scalar 分别负责什么？
- 为什么各管线时间不能直接相加？

### 2.3 瓶颈是什么

- 当前是计算受限、带宽受限，还是调度/标量指令受限？
- 为什么 Cube 活跃时间只有约 2.85%，但 Cube wait 又达到约 36.87%？
- 增加 Cube 利用率是否一定能缩短总时间？

### 2.4 如何科学地优化

- 如何选择 `baseN/baseK/l1K`？
- 双缓冲为什么可能有效，又为什么可能无效？
- 如何区分真实优化、测量波动和 profiling 失真？

### 2.5 如何交付一个优化结果

- 精度不回归；
- 性能可复现；
- 每个结论有 profiling 数据支撑；
- 能解释负优化和优化边界。

## 3. 推荐学习路线

可以安排为 **4～6 周**，每周集中解决一类问题。

### 阶段 1：读懂算子，建立软硬件映射

#### 学习内容

先逐行读懂：

```text
matmul_m1.py
└── torch_npu.npu_matmul_lyc_custom
    └── op_extension
        └── op_host
            ├── 查询 Cube 核数
            ├── 计算 Tiling
            └── 启动 kernel
                └── op_kernel
                    ├── GM → L1
                    ├── L1 → L0A/L0B
                    ├── Mmad
                    ├── L0C → UB
                    └── UB → GM
```

重点理解这些 Buffer：

| Buffer | 所在存储 | 需要掌握的问题 |
|---|---|---|
| A1/B1 | L1 | 为什么 B1 比 A1 大很多？为什么使用两块 Buffer？ |
| A2/B2 | L0A/L0B | Mmad 对输入布局和分形有什么要求？ |
| CO1 | L0C | 为什么使用 FP32 累加？ |
| cUb | UB | 为什么需要经过 UB，而不是直接写 GM？ |
| zeroUb | UB | M=1 为什么还要构造 16 行输入？ |

#### 实践任务

手工计算一个 N tile 的：

- GM 读取字节数；
- L1、L0A、L0B、L0C、UB 占用；
- K 循环次数；
- Mmad 调用次数；
- 最终有效输出行数。

再计算整个算子的理论数据量：

```text
A：1 × 7168 × 2 ≈ 14 KB
B：7168 × 16160 × 2 = 231,833,600 字节 ≈ 221.1 MiB
C：1 × 16160 × 2 ≈ 31.6 KiB
```

有效计算量约为：

```text
2 × M × N × K = 231,669,760 FLOPs
```

只考虑必须读取一次的 B，有效算术强度约为：

```text
231,669,760 / 231,833,600 ≈ 1 FLOP/Byte
```

#### 阶段验收

不看代码，也能画出数据流图，并解释：

> 这个算子虽然调用 Cube/Mmad，但 M=1 导致有效算术强度很低，因此首先应该怀疑数据搬运瓶颈，而不是 Cube 算力不足。

- 同一版本重复采集，结果稳定；

### 阶段 3：学会用 profiling 提出假设

当前完整采集的核心数据是：

| 指标 | 当前值 | 应如何理解 |
|---|---:|---|
| Task Duration | 2676.762 μs | 本次单算子采集任务时间 |
| aic_time | 2615.584 μs | AI Core 侧统计时间 |
| Cube active | 74.628 μs，2.85% | Cube 实际活跃占比较低 |
| Scalar active | 905.685 μs，34.63% | 地址、循环和控制指令值得关注 |
| MTE1 active | 223.585 μs，8.55% | L1 到 L0 等搬运需要结合代码分析 |
| MTE2 active | 2593.450 μs，99.15% | 当前最突出的数据搬运输送占用 |
| MTE3 active | 27.847 μs，1.06% | 输出写回不是主要矛盾 |
| Cube wait | 36.87% | Cube 有较多等待，需要结合上游供数分析 |
| MTE1 wait | 34.54% | MTE1 也存在等待或依赖 |

#### 最重要的学习原则

这些管线是并行工作的。例如：

```text
Cube 74.6 μs
Scalar 905.7 μs
MTE1 223.6 μs
MTE2 2593.4 μs
```

不能相加后得到总耗时，也不能简单认为：

> 把 Scalar 减少一半，就能节省约 450 μs。

只有位于关键依赖链上的时间减少，才可能转化为端到端收益。

#### 实践任务

依次写出假设，并注明验证方法：

```text
假设 H1：B 的 GM→L1 搬运是主要瓶颈。
验证：比较不同 Tiling 下总时间、MTE2 活跃时间和指令数。

假设 H2：L1 预取深度不足，导致 MTE2 与 Mmad 重叠不充分。
验证：只改变 l1K 或预取策略，观察 Cube wait 和总时间。

假设 H3：循环和地址计算产生过多 Scalar 指令。
验证：只减少标量计算，观察 Scalar 时间和总时间是否同步改善。

假设 H4：101 个 N tile 在 8 核上存在尾部负载不均。
验证：分析每核分配 tile 数，并尝试不同的任务划分。
```

#### 阶段验收

不再停留在“MTE2 高，所以优化 MTE2”，而是能形成：

> **观测现象 → 代码位置 → 影响机制 → 单变量实验 → 预期指标变化**

### 阶段 4：系统学习 Tiling 优化

这是最适合新人的第一组优化实验。

#### 实验顺序

严格一次只改一个变量：

1. 只改变 `l1K`；
2. 只改变 `baseK`；
3. 只改变 `baseN`；
4. 最后才尝试组合参数；
5. 比较双缓冲和预取深度变化。

每个实验同时检查：

- L1/L0A/L0B/L0C/UB 是否放得下；
- K、N 是否整除；
- B 的分形布局是否正确；
- 队列深度是否足够；
- 不同核的任务分配是否均衡；
- 精度是否保持。

#### 需要理解的权衡

| 参数变化 | 可能收益 | 可能代价 |
|---|---|---|
| 增大 `l1K` | 减少外层循环和同步次数，扩大预取粒度 | L1 占用增加，双缓冲可能放不下 |
| 增大 `baseK` | 减少 Mmad 和内部循环次数 | L0A/L0B 压力增加，等待关系可能变化 |
| 增大 `baseN` | 减少 N tile 数和部分控制开销 | B1/B2/CO1/UB 占用显著增加 |
| 减小 tile | 降低存储压力，增加并行任务数 | 搬运、循环和启动控制开销增加 |
| 增加预取 | 提高搬运与计算重叠机会 | Buffer 占用和依赖管理更复杂 |

#### 阶段目标

不要以“找到最大参数”为目标，而要找到：

> **存储容量、搬运粒度、并行度和同步开销之间的平衡点。**

建议至少完成 **8～12 组单变量实验**，包括失败实验。

### 阶段 5：学习流水线和数据布局优化

完成 Tiling 后，再进入代码结构优化。

#### 可研究的方向

1. **检查双缓冲是否真正重叠**
   - 当前 `Wait`、`EnQue`、`DeQue` 的顺序是否形成串行依赖？
   - 预取是否足够早？
   - 某一级 Buffer 是否成为流水线瓶颈？

2. **减少 Scalar 工作**
   - 循环内是否存在可以外提的地址计算？
   - 是否有重复的分形坐标计算？
   - 是否可以减少运行时除法、取模和复杂条件判断？

3. **分析 B 的布局转换成本**
   - GM 中是 ND；
   - L1 中构造 zZ；
   - L1→L0B 又通过 transpose 转成 nZ。
   - 需要弄清楚这些转换分别由哪些指令和管线承担。

4. **分析尾部负载**
   - `nTiles=101`、`blockNum=8`；
   - 每核先执行 12 个 tile 后，还有 5 个核需要执行第 13 个；
   - 需要判断尾部不均是否值得通过改变 N 划分改善。

5. **比较不同的数据通路**
   - 当前使用 L0C→UB→GM；
   - 可以研究其他路径是否适用于 DAV_2002，但必须先确认硬件约束，不能直接照搬其他芯片示例。

#### 阶段验收

每次优化都要回答：

- 减少了什么指令或数据搬运？
- 改变了哪条依赖链？
- 哪个 profiler 指标应该变化？
- 实际总时间是否变化？
- 如果指标改善但总时间没变，原因是什么？

### 阶段 6：进阶——重新审视算法是否适合 Cube

当你熟悉现有实现后，可以做一个更有价值的专题：

> **M=1 时，补成 16×K 后调用 Mmad，是否是最合适的技术路线？**

当前实现为了适配 Cube：

- 有效输入只有 1 行；
- 实际 Mmad 按 16 行执行；
- Cube 的有效计算利用率天然受到 M=1 限制。

不过，这不代表 Vector 实现一定更快，因为 B 仍然需要搬运约 221.1 MiB，最终性能可能仍由内存路径决定。

可以设计两个研究版本：

```text
版本 A：现有 Mmad/Cube GEMV
版本 B：以 Vector 乘加和归约为核心的 GEMV
```

比较：

- 总 Device 时间；
- MTE2 活跃时间；
- Scalar 时间；
- Vector/Cube 时间；
- 代码复杂度；
- 不同 N、K 下的适用性。

这个专题的目标不是必须战胜现有实现，而是学会：

> **根据 shape 选择硬件执行单元，而不是看到 MatMul 就默认使用 Cube。**

## 4. 可量化学习目标

### 4.1 初级目标

- 能独立编译、运行和验证算子；
- 能解释所有 Buffer 和 Tiling 参数；
- 能区分 Host 墙钟、Device task、aicore time；
- 能正确生成并阅读 `op_summary`、`task_time` 和 `PipeUtilization`；
- 不把 replay 墙钟或累计管线比例误当成总耗时。

### 4.2 中级目标

- 完成至少 10 组单变量实验；
- 至少详细分析 2 个“指标改善但性能没有改善”的案例；
- 找到当前实现的 2～3 个主要性能限制；
- 在不回归精度的前提下，争取获得 **10% 以上可复现的 Device 性能改善**。

10% 是学习目标，不是保证。如果最终无法达到，也应能够用数据证明：

- 已接近某个硬件限制；
- 或现有瓶颈无法通过当前优化手段解除；
- 或需要改变算法/数据通路。

### 4.3 高级目标

- 能比较 Cube 与 Vector 两条 GEMV 路线；
- 能建立简单的带宽下界或 Roofline 分析；
- 能把优化方法迁移到新的 M/N/K；
- 能为算子编写自动化的正确性、性能和参数扫描测试。

## 6. 第一条实践主线

最重要的能力不是背下某个最优参数，而是能够重复完成：

> **测量 → 假设 → 实验 → 验证 → 归因**

对当前这个算子，建议首先围绕 **MTE2 接近满活跃、Cube 低活跃且存在等待** 展开，暂时不要把主要精力放在 Host 端几微秒的开销上。
